# Data Formats

Specifications for all JSONL formats produced and consumed by apisynth.

---

## training.jsonl

One JSON object per line. Written by `run.py`, enriched by `add_thinking.py`.

### Schema

```json
{
  "question":        "Natural language prompt (string)",
  "schema":          "Endpoint schema text (string, optional — see below)",
  "thinking":        "Structured reasoning trace (string, optional)",
  "intent_category": "Intent type tag (string, optional — see below)",
  "api_call":  {
    "endpoint": "HTTP method + path template (string)",
    "params":   {"paramName": "value", ...}
  }
}
```

For chained (two-step) calls:

```json
{
  "question": "show me a program",
  "thinking": "Goal: retrieve a specific program...",
  "api_call": {
    "steps": [
      {"endpoint": "GET /external/v1/content/programs", "params": {}},
      {"endpoint": "GET /external/v1/content/programs/{programId}",
       "params": {"programId": "{{steps.0.programId}}"}}
    ]
  }
}
```

### Field details

**`question`** — The natural language input. Generated by `gen_questions()` from phrasing
templates. One question per record; the same API call may appear under many different questions.

**`schema`** — Concise text description of the endpoint's parameters, extracted from
`config.yaml` by `extract_schema()` in `utils.py`. Included so a fine-tuned model can learn
to read the schema at inference time rather than memorising parameter names from training
(retrieval-aware training per Gorilla, NeurIPS 2024). Example:
```
GET /external/v1/content/episodes
params: pageSize (integer), networkId (integer), programId (integer)
path params: (none)
```
At inference time, the caller retrieves the relevant schema and includes it alongside the
question in the model's context. `prepare_data.py` in trainLLM should embed this field in
the user message or system prompt when building conversation records.

**`intent_category`** — Tag classifying the query's intent type, set by `infer_intent()` in
`utils.py`. Used for intent-stratified evaluation splits. Values:
- `bare-list` — list endpoint, no meaningful params
- `paginated` — list endpoint with pageSize only
- `filtered` — list endpoint with non-pageSize filter params
- `by-id` — single-item lookup via path param
- `chained` — multi-step call (has `steps`)
- `no-param` — endpoint with no params (e.g. `/me`)

**`thinking`** — Structured reasoning trace. Added by `add_thinking.py`. Always one of:
- Linear format (Entity/Scope/Use/NOT):
  ```
  Entity: program
  Scope: single item -- the prompt contains an explicit ID (42)
  The number 42 is the programId, not a page number or filter
  Use:    GET /external/v1/content/programs/{programId}
  NOT:    GET /external/v1/content/programs (that is the list endpoint)
  Params: {"programId": 42}
  ```
- QOC format (Question/Option/Criteria):
  ```
  Question: Retrieve a single program by ID, or list all programs?
  Option A: GET /external/v1/content/programs/{programId}  (single item)
  Option B: GET /external/v1/content/programs  (list — no ID needed)
  Criteria: Prompt contains explicit numeric ID '42'. Option A wins.
  Params:   {"programId": 42}
  ```

**`api_call.endpoint`** — HTTP method + path template, e.g.
`"GET /external/v1/content/programs/{programId}"`.
Path params appear as `{paramName}` placeholders.

**`api_call.params`** — Query and path param values. Path params are included here
alongside query params. For chained calls, step references use `{{steps.N.fieldName}}`
syntax (double braces).

## holdout.jsonl

Evaluation records. Written by `prepare_data.py` (in trainLLM), preserved across
regenerations for canonical and MCP-log records.

### Schema

```json
{
  "id":                 "canonical-0001",
  "label":              "Get program 42",
  "messages": [
    {"role": "system",    "content": "You are an <vendor> API assistant..."},
    {"role": "user",      "content": "Get program 42"},
    {"role": "assistant", "content": "<think>\n...\n</think>\n```json\n{...}\n```"}
  ],
  "conventions_tested": ["program", "by-id"]
}
```

**`id`** — Prefix indicates origin:
- `canonical-NNNN` — from the 70-question test suite (preserved across regenerations)
- `mcp-log-NNNN` — from real production MCP call logs (preserved)
- `<endpoint>-NNNN` — auto-generated from training data split

**`conventions_tested`** — Tags for grouping eval results. Common values:
`by-id`, `bare-list`, `synonym`, `disambiguation`, `natural-phrasing`, `bare-noun`,
`bare-form`, `page-size-only`, `filtered`, `no-params`, `real-world-mcp`.

## router_train.jsonl / router_test.jsonl

Training and test data for the intent router classifier.

### Schema

```json
{"question": "list all programs", "route_key": "acme/api/programs"}
{"question": "Get program 42",    "route_key": "acme/api/program"}
```

**`route_key`** — Hierarchical identifier: `{vendor}/api/{endpoint_name}`.
Singular names (`program`, `episode`) indicate by-ID endpoints.
Plural names (`programs`, `episodes`) indicate list endpoints.
The top-level router key (`acme/api`) is a special case used by the LoRA router adapter.

## dpo.jsonl

DPO (Direct Preference Optimization) preference pairs. Used to suppress specific
hallucinations when SFT alone is insufficient.

### Schema

```json
{
  "question": "list campaigns",
  "chosen":   {"endpoint": "GET /external/v1/measurements", "params": {}},
  "rejected": {"endpoint": "GET /external/v1/campaigns",    "params": {}}
}
```

**`chosen`** — The correct API call.
**`rejected`** — The wrong API call the model tends to produce (the hallucination to suppress).

Multiple rejected examples for the same question are written as separate records with
the same `question` and `chosen` but different `rejected` values.

## Code-path formats

The repo/code path (see [REPO_SOURCES.md](REPO_SOURCES.md)) emits records with a `type: "code"`
discriminator and a structured `output` dict instead of an `api_call`. These are produced by
`scripts/repo/*` and `scripts/repo_pipeline.py`, and verified offline by the code rubric in
`eval.py` rather than by a live API.

### Code training.jsonl

Written by `generate_from_code.py` (via `repo_pipeline.py`). One JSON object per line.

```json
{
  "type": "code",
  "question": "How do I use `scan_repo`?",
  "thinking": "Entity: function scan_repo\nFile: scripts/repo/scan_repo.py\nScope: single unit -- top-level function\nUse: call scan_repo(config)",
  "output": {
    "unit": "function",
    "name": "scan_repo",
    "file": "scripts/repo/scan_repo.py",
    "signature": "scan_repo(config)"
  }
}
```

**`type`** — Always `"code"` for code-path records (distinguishes them from API-path records).

**`output`** — The structured answer. Required keys:
- `unit` — one of `function`, `method`, `class`, `api_call` (mirrors the scanner's unit type).
- `name` — the identifier.
- `file` — repo-relative POSIX path to the defining file.
- `signature` — best-effort signature string (a definition fragment for defs; a call-site form
  for `api_call`).
- `class` — present **only** for `method` units; names the parent class.

**`thinking`** — Deterministic reasoning trace generated from the known-correct `output` (linear
by default, QOC when `thinking_style: hybrid`). Never distilled from a teacher model.

**`source`** — Optional provenance tag. `"evol"` on records produced by `evolve_code_questions.py`
(which also add `evol_axis` and `evol_seed`); `"bootstrap"` on records produced by
`bootstrap_code_traces.py`. Absent on freshly generated records.

**Holdout split** — Deterministic. The default `hash` strategy assigns a unit to holdout when
`sha256("<file>:<name>") / 2**256 < holdout_ratio` (stable across processes and `PYTHONHASHSEED`,
never the salted builtin `hash()`). The optional `stratified` strategy holds out exactly
`round(holdout_ratio·n)` units per unit type. Holdout records share this schema and are written to
`holdout.jsonl` alongside `training.jsonl`.

### Code dpo.jsonl

Written by `gen_code_dpo.py`. The `chosen`/`rejected` values are `output` dicts (not API calls).

```json
{
  "type": "code",
  "question": "How do I use `scan_repo`?",
  "chosen":   {"unit": "function", "name": "scan_repo", "file": "scripts/repo/scan_repo.py", "signature": "scan_repo(config)"},
  "rejected": {"unit": "function", "name": "scan_repo_TYPO", "file": "scripts/repo/scan_repo.py", "signature": "scan_repo(config)"}
}
```

**`chosen`** — The correct `output`. **`rejected`** — a deterministically corrupted, strictly-worse
variant (differs from chosen AND is either malformed or has `field_accuracy < 1.0`). One pair is
written per source record.

### Code router_train.jsonl / router_test.jsonl

Written by `gen_code_router_data.py`. Same `{question, route_key}` shape as the API router, but the
`route_key` is the unit's relative **file path** (`output["file"]`) — "which file does this question
target" — rather than `vendor/api/name`.

```json
{"question": "How do I use `scan_repo`?", "route_key": "scripts/repo/scan_repo.py"}
```

Split with a fixed `SEED = 42` and `TRAIN_RATIO = 0.8`. Trained by `train_code_router.py` into
`code_router_classifier.joblib`.

## ShareGPT format (prepare_data.py output)

The format expected by trainLLM for SFT. Produced by `prepare_data.py`.

```json
{
  "conversations": [
    {"from": "system", "value": "You are an <vendor> API assistant..."},
    {"from": "human",  "value": "Get program 42"},
    {"from": "gpt",    "value": "<think>\nEntity: program\n...\n</think>\n```json\n{...}\n```"}
  ]
}
```

The `gpt` field contains the full model response: the `<think>` block (if `thinking` was
present in the source record) followed by the JSON code block.

## Notes on path param conventions

In `api_call.params`, path params and query params are stored together. The caller
(e.g., `run_one()` in `run.py`) separates them based on `path_params` in the config:

```python
# path param   → goes into the URL path: /programs/42
# query param  → goes into the query string: /programs?pageSize=10
```

In chained calls, `{{steps.0.fieldName}}` is resolved at runtime by replacing it with
the value of `fieldName` from the first step's API response.
